A 4-lens adversarial review of the bundle caught + fixed two more: (i) a REGRESSION where the now-variable retry amount collided with the constant `cleaner-payout-<id>` idempotency key after a lost-response stranded transfer (400-loop or 24h double-pay) → the carved-slice retry now ADOPTS an existing group transfer for the cleaner instead of re-issuing (generalizes the H4 repair to cover a NULL transfer_id); (ii) a silent-loss residual where Stripe being unreadable at retry made a PARTIAL refund read as zero → the refunded-total fallback now consults the local `refunds` ledger before the terminal `payments.status='refunded'`.
- [ ] **T1-14 · MEDIUM · Owner-alert completeness + delivery robustness.** From the PR #187 Codex review (verified). (a) Two owner-actionable events are recorded but absent from `ALERTABLE_PAYMENT_EVENTS`, so the owner is never told: `refund_ledger_write_failed` (Stripe refund succeeded but the `refunds` insert failed → later refundable-amount math can over-refund; `refund/route.ts:137`, `paymentEventAlerts.ts:24`) and `late_payment_failure` (settled ACH debit returned after transfers paid; latent until ACH; `dispatchStripeEvent.ts:347`). (b) `platformAlert.ts` substrate robustness: the owner-webhook `fetch` is awaited with NO timeout on the money path (a hung endpoint stalls a Stripe webhook past its deadline → retries; `platformAlert.ts:120`); Supabase `error` fields on the select/update/insert are ignored, so a failed alert persist is swallowed (only the console log survives; `:76-105`); the webhook fires on every occurrence regardless of dedupe (spam; `:60`); and the select-then-update dedupe has no unique open-incident constraint (dup rows / one lost occurrence bump under concurrency). All pre-existing, all mitigated by the always-on `console.error` channel. Owner-view route Lows (owner-only): literal `null` JSON body → 500 (`alerts/[id]/route.ts:29`), non-UUID id → 500 not 400, unknown `?status=` returns all. → Add the two event types to the map; add an AbortSignal timeout + surface persist errors; consider a unique partial index for open incidents.
- [ ] **T1-15 · LOW · T1-1 sweep residual hardening (Codex review, not in the #187 follow-up commit).** All verified, all low-probability at current scale: (a) preflight `continue` paths (no PI / unreadable charge / list threw) write no marker or fresh failure, so a permanently-unreadable OLD appointment can occupy the oldest-first RPC batch every sweep — terminalize to manual review after N fruitless reconciler touches (`reconcile.ts:764,778,807,825`); (b) a divergent-target concurrency race survives the freshness snapshot (a refund arriving AFTER the newest-refund check lets the sweep's stale target + the live path's fresh target both reverse → over-reversal; needs a per-appointment lock or a re-read of `amount_refunded` immediately before reversing; `reconcile.ts:780,815`); (c) SQL backoff counts failed LEGS not sweeps (a two-leg failure doubles the delay twice) and measures from the newest failure ≤ cutoff, not the absolute newest (`migration 112:63`, `reconcile.ts:730`); (d) terminal `refund_unwind_manual_review` alerts key per-org so two appointments collapse into one row with overwritten details and never re-alert — include appointment id in that key (`paymentEventAlerts.ts:68`); (e) `listTransfersByGroup` ignores `has_more` (>100-transfer group could be marked recovered while truncated; `transfers.ts:55`). **Fixed already in #187 follow-up:** failed/canceled refunds excluded from the guards, same-second `>=` boundary, and a critical alert when the candidate RPC itself fails.
