# Payments Audit v4 — Findings Backlog

Money-code audit run 2026-07-16 (multi-agent, adversarially verified). Scope: every money path (charge, split, transfer, refund, clawback, webhook, reconcile) plus admin/homeowner visibility and notifications. **Goal: fix all of these before/around MVP.** Bridger intends to work through every item.

- **Full evidence + verifier verdicts for each item:** `docs/payments-audit-v4-findings-detail.md` (file:line citations, failure scenarios, verifier corrections).
- **Status legend:** `[ ]` todo · `[~]` in progress · `[x]` done. `CONFIRMED` = survived adversarial verification. `⚠ unverified` = auditor found it but the verifier agent didn't run before the audit was stopped (many are corroborated by a second domain's auditor — noted inline). Verify these against current code before fixing.
- **Flag state at audit time (prod):** `STRIPE_TENANT_CONNECT_ENABLED`=true, `STRIPE_NEW_CHARGE_FLOW_ENABLED`=true, ACH + self-pay + fee-passthrough-UI states per `stripe/flags.ts`. ACH and self-pay paths are OFF in prod → their findings are "block the flag-flip," not "block MVP."
- **Caveat:** audit ran on the `feat/platform-fee-1pct` worktree. A few homeowner-notification gaps may already be partly closed on `master` (e.g. PR #161 charge-failed bell). Re-check against master before starting item 11.

## Tier 1 — Live in prod, money moves wrong (highest priority)

- [ ] **T1-1 · CRITICAL · Failed transfer reversal during refund unwind: no retry, no alert, platform permanently out the money.** Refund pays homeowner from platform balance first; if the tenant/cleaner reversal then throws, it records `transfer_reversal_failed`/`refund_clawback_failed` to `payment_events` (unread), marks the webhook processed, and the sweep only retries a *different* event type. `src/lib/payments/clawback.ts:331`, `reconcile.ts:589`, `refund/route.ts:155`. CONFIRMED. → Add a bank_paid-style guard + a retryable dead-letter path for these two event types + an alert.
- [ ] **T1-2 · HIGH · Refund silently reverses cleaner transfers already `bank_paid`, bypassing the deliberate clawback-blocked policy.** `reverseJobTransfersForRefund` has no bank_paid guard (unlike `clawbackCleanerPayout`), drives the cleaner's connected balance negative, and overwrites status bank_paid→reversed. With daily payouts, ~every refund >2 days post-completion hits this. `src/lib/payments/clawback.ts:296`. CONFIRMED. (Doubly latent today because of T1-3.)
- [ ] **T1-3 · HIGH · `bank_paid` is unreachable in prod.** Live webhook doesn't subscribe `payout.paid`/`payout.failed`/`transfer.reversed`; fallback route `/api/stripe/connect/reconcile-payouts` has zero callers (caller removed in PR #46); no cron bank-paid job. Payout status lies at "paid" forever; `cleaner_paid` + `clawback_blocked` are dead code; bank-level payout failure changes nothing. `src/app/api/stripe/connect/reconcile-payouts/route.ts`, `reconcile.ts` job list. CONFIRMED. → Subscribe events (cutover step) AND add a reconcile job; wire the fallback route to a caller or delete it.
- [ ] **T1-4 · HIGH · Settlement race splits the Stripe fee.** `payment_intent.succeeded` can arrive before the charge route writes the payments row; settlement then reads `processing_fee_cents`=0 and over-splits the grossed-up amount (~3%) to tenant+cleaner; sweep then double-handles the repair. `src/lib/payments/settleCleanerPayout.ts:122`, `chargeCompletedAppointment.ts:538`. CONFIRMED (verifier: worse than reported — leaves `transfer_amount` null too). → Settle only after the payments row exists, or derive fee from the PI in the webhook.
- [ ] **T1-5 · HIGH · Manual "Record payment" enables double collection.** Never clears `authorization_status`, coexists with the failed Stripe row; booking stays in triage with "Retry charge"; `alreadySettled`'s unordered `.limit(1)` can miss the paid cash row → real card charge on top of collected cash. `src/app/api/payments/record/route.ts:51`, `chargeCompletedAppointment.ts:200`. CONFIRMED. → Clear auth status on manual record + add an already-paid guard + order the `alreadySettled` query.
- [ ] **T1-6 · HIGH · Configured no-show fee is never charged.** Cancel route reads only `cancellation_fee_*`; `no_show_fee_type/value` exist only in settings UI + settings route. "Free cancels, $50 no-show" charges $0 on every no-show, silently. `src/app/api/appointments/[appointmentId]/cancel/route.ts:127`, `cancellationFee.ts:31`. CONFIRMED. → Read + apply the no-show columns (design doc #10 originally specified one fee; migration 071 + settings added a second that money code never wired up).
- [ ] **T1-7 · HIGH · Completed job that bails on charge preconditions is invisible & sometimes uncollectable.** `no_card`/`tenant_not_ready` bails write no failed status, no notification, no queue entry; the `payment_method_id NULL` subcase is also excluded from the sweep and card-link self-heal → nothing automated can ever collect it. `src/lib/payments/chargeCompletedAppointment.ts:295`. CONFIRMED. → Stamp a visible state + notify on these bails; include NULL-PM rows in a manual-attention surface.
- [ ] **T1-8 · HIGH · Reconciler findings alert nobody.** `payment_events` is write-only (no UI/hook/route reads it); `recordPlatformAlert` (+ its Slack sink) is called only by forgot-password; pg_cron discards the sweep's JSON result. Money-math violations, tenant-transfer failures, stranded clawbacks, fraud warnings all detected → silent. `src/lib/payments/reconcile.ts:546`, `monitoring/platformAlert.ts`. CONFIRMED. → This is the balance-floor monitor already queued as a platform-fee follow-up. Wire alerts into these paths + capture the cron result.
- [ ] **T1-9 · HIGH · Tenant transfer failed (org not paid) has no surface at all.** No payout row, no triage entry, no notification, no platform alert — only a `payment_events` row. Exact recurrence path of the prod negative-balance incident. `src/lib/payments/settleCleanerPayout.ts:188`. ⚠ unverified (verifier didn't run) but mechanically corroborated by the webhooks-domain audit. → Depends on T1-8; add a visible state for the tenant leg.
- [ ] **T1-10 · HIGH · Dead-letter retry can never recover Connect-delivered events.** `retrieveStripeEvent` omits the `Stripe-Account` header though `account_id` is stored; `payout.paid/failed`, `account.updated` 404 forever; ascending-FIFO batch of 100 can be permanently starved by dead rows. `src/lib/payments/reconcile.ts:72`, `stripe/reconcile.ts:12`, `webhookIdempotency.ts:35`. CONFIRMED. → Pass stored `account_id`; add a terminal "dead" status so starved batches drain.
- [ ] **T1-11 · MEDIUM · Fixed transfer idempotency keys lock out payout retries for ~24h after a failure.** `tenant-payout-`/`cleaner-payout-` keys have no attempt counter; after `balance_insufficient` the admin Retry button + ~96 sweep retries replay Stripe's cached failure until the key ages out. Charges already solved this with attempt-suffixed keys. `src/lib/payments/settleCleanerPayout.ts:177,322`. ⚠ unverified but cited contrast code is explicit. → Attempt-suffix the transfer keys.
