# Cleaner app redesign, Slice 4: Earnings (design spec)

**Date:** 2026-06-28
**Branch:** `feat/redesign-cleaner-app-slice4` (worktree off `master` @ #97)
**Status:** design approved (brainstormed with Bridger 2026-06-28), ready for implementation plan.
**Spec context:** Slice 4 of the 6-slice cleaner (field-worker) app redesign. See `docs/superpowers/specs/2026-06-26-redesign-cleaner-app-design.md` (overall design, §5.4 Earnings + §8 reuse map + §9 slice cut) and `docs/superpowers/cleaner-app-status.md` (where we are).

## 1. Goal

Replace the Earnings tab placeholder (`src/app/(redesign)/app/cleaner-dashboard/earnings/page.tsx`, currently a "coming soon" `EmptyState`) with the real phone-first Earnings screen for the contractor (`percentage_contractor`) model. It answers a field worker's two questions: **how much am I getting, and when.** Reuse-everything: NO new data layer, NO new API routes, NO migration.

## 2. The governing principle (decided this brainstorm)

**Stripe owns every money number.** Available balance, money in transit to the bank, and paid-out history all come from Stripe's embedded payouts component, never from our database aggregates. We deliberately deleted our white-label balance cards once before (`project_payouts_stripe_embed`) for this reason; this slice holds that line. Do **not** surface `useCleanerStats.totalEarnings` / `pendingPayouts` or any of our own money aggregates as headline figures.

There is exactly **one** money concept Stripe's cleaner view cannot show, and it is the only money figure we contribute: **a job whose customer payment has not settled yet.** In the charge-at-completion flow the cleaner's cut only transfers into Stripe after the customer's charge clears; for card the charge usually settles immediately (but can sit in `processing`), and for **ACH it takes several business days**, during which the job is done and the cut has not hit the cleaner's Stripe balance. That is the "Still clearing" section. It is *upstream* of Stripe, so it never duplicates or competes with the Stripe numbers. (`useCleanerAwaitingPayments` filters `status='processing'` + `payment_type='revenue'` with **no** method filter, so card-`processing` rows can appear too; the settle copy must be method-aware, not a blanket "4 business days" claim, see §3.)

Everything else on the screen is non-money **activity** (job counts), which is safe to compute from our data because it is not money.

## 3. Screen anatomy (connected, money flowing)

Phone-first single column inside the existing `CleanerShell` (the shell already provides the top bar, the 5-tab bottom nav, the `max-w-lg` phone column, the skip link, and `pb-28`; the screen adds only vertical spacing, never chrome or width). Top to bottom:

1. **Payout timing note** — the reused one-time, dismissible `PayoutTimingNotice` ("First payout in 7 to 14 days, then about 2 business days."). localStorage-persisted; comes free with the reuse.
2. **Payouts to your bank** (STRIPE, authoritative) — a redesign-tokenized `Card` wrapping the embedded Stripe `ConnectPayouts` table (available balance, money on the way to the bank, paid-out history) with an **Open Stripe** action (`handleOpenStripeDashboard`). This is the money. We never hand-build balance numbers.
3. **Still clearing** (OURS, pre-Stripe) — list of jobs whose customer payment is still settling. Each row: service name; the customer label rendered straight from `row.appointment.homeownerName` (already `"Company-paid"` for self-pay, do NOT pass it through `customerLabel`, which takes a `CleanerAppointment`, not an awaiting row); the date via `formatCardDate(scheduledDate, todayStr)` (the row exposes `scheduledDate`/`createdAt`, there is no dedicated completed-at field); the reused **`TxnStatusBadge badge="processing"`** ("Clearing", `info` variant, spinning `Loader2`, privacy-neutral, NOT the amber `caution`); and the cleaner's **expected** cut (right-aligned, `tabular-nums`, labeled *expected/pending* so it reads as a placeholder, never a balance, until Stripe confirms). Settle copy is **method-aware** (ACH: "Settling, about 4 business days"; card-`processing`: "Settling") rather than one blanket note, so a card row is never mislabeled. The whole section is **hidden when the list is empty** (legacy parity). Decision: amounts are shown (Bridger: they are the cleaner's own cut, accurate). NOTE: the query has no `appointment.status` filter, so a `processing` row on a cancelled-after-ACH appointment can transiently appear (the known cancel-during-ACH-debit gap); acceptable until that gap closes (see §11).
4. **Activity** — three count tiles: **This week**, **Completed**, **Upcoming**. Counts only, no money. Build these as a small **local tile** (`Card` + tokens) or the inline count idiom already used by `CleanerTodayView`/`CleanerScheduleView`, **NOT** the operator `StatTile` (that is the desktop KPI primitive and clashes with the phone-first feel and Bridger's prior "no KPI row" steer). (Bridger: keep these; Stripe + clearing already give enough money detail.)

## 4. States to design (all of them)

The screen is a state machine over (a) the feature flags, (b) auth/org gating, (c) the Stripe Connect onboarding state, and (d) whether there is anything to show.

- **Flag-off (prod):** the entire `(redesign)` tree is `notFound()`-gated centrally in `src/app/(redesign)/layout.tsx` via `redesignUiEnabled()` (`NEXT_PUBLIC_REDESIGN_ENABLED`); preview/dev always allowed. The Earnings screen itself does **not** re-check the flag.
- **Auth / org gating:** handled by the cleaner-dashboard layout (spinner while loading, workspace-error screen on org error, non-cleaners redirected). The screen renders only after.
- **Stripe disabled** (`NEXT_PUBLIC_STRIPE_ENABLED !== "true"` / no publishable key / not cleaner role): the embed slot shows `CleanerStripeConnect`'s own "Payout setup isn't available yet" placeholder, and the Container **suppresses the "Get paid for your work" framing card** in this case (the button would lead nowhere). The Container can gate the card on the same pure check (flag + key + role) without calling `useCleanerConnect`. Still show "Still clearing" + activity if present.
- **Connect status loading (first paint only):** design-system `Skeleton` stack (a card-height block for the payouts slot, row skeletons for clearing, pill skeletons for the count tiles). Never a bare spinner in the content column. The screen-level skeleton keys off **first-paint `isLoading` (not `isFetching`)** so a background status refresh never re-toggles it (the iframe-unmount invariant, below). Once the embed mounts, the payouts-slot skeleton is owned by the embed's own `StripeFramedCard loading` state; do not also stack a screen-level skeleton over it (avoid the sequential double-skeleton flash).
- **Not set up yet** (`cleanerStatusKind === 'inactive'`, no Stripe account): the redesign-native **"Get paid for your work"** card (bank icon, comforting copy, single **Set up payouts** primary button). The button reveals Stripe's embedded onboarding inline (`ConnectAccountOnboarding`, the legacy "CTA reveals inline embedded onboarding" pattern); our card is the *entry/framing*, Stripe's component is the actual onboarding UI. Plus, if the cleaner already has completed-but-unpaid jobs, a **"Waiting for you"** variant of the clearing list with "Connect your bank to receive this." (a deliberate pull toward setup). Activity tiles still shown. (Bridger explicitly liked this state's wording: automatic payment is a core promise of the app and this makes setup the obvious click.)
- **Setup unfinished / pending verification / restricted** (`cleanerStatusKind === 'pending'`, the single bucket): same card shape with "Finish payout setup" / "Verifying your details" copy and a continue action into the embedded onboarding. The specific requirement is surfaced by Stripe's **`ConnectAccountOnboarding`** flow itself (NOT a separate banner, `CleanerStripeConnect` does not render `ConnectNotificationBanner`); we do not re-derive requirement detail. NOTE: `cleanerStatusKind` maps restricted -> `pending` only because the account-status route folds `payouts_enabled` into `onboarding_complete` (it does not read `payouts_enabled` directly); this dependency is intentional. A cleaner restricted *after* going active is pushed back to onboarding and loses balance visibility until it is resolved (accepted).
- **Active + payouts enabled** (`cleanerStatusKind === 'active'`): the full screen in §3. (An active cleaner under a Stripe grace-period requirement sees `ConnectPayouts` with no banner; surfacing that would mean adding `<ConnectNotificationBanner/>` above the table. Optional, deferred.)
- **Empty (connected, nothing yet):** there is **no separate top-level `EmptyState`** in the connected path. The activity tiles always render (counts, even at 0) and the payouts `Card` always renders (the Stripe table shows its own zero state), so the connected screen is never truly empty; a dedicated EmptyState would double up. "Still clearing" simply hides when empty. (The `EmptyState` primitive stays on the placeholder page until this ships, and would only be reused if a future state were genuinely contentless.)
- **Errors:** `useStripeConnect.connectError` (inline non-fatal banner above the embed; embed still shows), `useCleanerConnect.initError` (replaces the embed with a graceful error box), and `useCleanerAwaitingPayments` / `useCleanerStats` errors (graceful inline treatment, no crash). There is no established cleaner-folder error primitive; use a small design-system-consistent inline message.
- **Employee / hourly model** (`organizations.default_payout_model === 'hourly_external'`): no Connect/payouts surface; a simple **"Your office handles your pay"** placeholder. Full employee model is deferred (Slice 6 / its own brainstorm); this is a placeholder only. NOTE: Slice 1 hardcodes `"percentage_contractor"`; wiring the real `default_payout_model` is a Slice 6 task, so for Slice 4 the contractor experience is the live path and the employee branch is built defensively but may not be reachable until Slice 6.

## 6. Privacy

The screen is **payout-only-safe in what it renders**: every displayed money figure is either Stripe's own (the cleaner's connected-account balance, inherently their money, and under the platform-held charge-at-completion model the connected account only ever receives separate cut-sized transfers, so `ConnectPayouts` and the Express dashboard show only the cut) or `cleanerCut` from `useCleanerAwaitingPayments` (already the cut). We never render the customer charge or the payout percentage. **Caveat (not closed by this screen):** `useCleanerAwaitingPayments` still selects `payments.amount` (the full charge) + `processing_fee_cents` to the browser to compute the cut client-side, so for a `payout_only` org the charge is present in the network response / TanStack cache even though no UI shows it. Genuinely closing that means computing `cleanerCut` server-side (reuse `presentChargeProjection`'s `payout_only` omission); it is the same deferred server-redaction item as the RLS gap below, not something this slice closes. (Known platform-level gap, out of scope: a cleaner's RLS still allows reading `payments.amount` directly; full DB-layer redaction is a separate, riskier payments-RLS change.)

## 7. Architecture (matches the redesign convention exactly)

Mirror `src/components/redesign/cleaner/today/` (page -> Container -> View -> derive + test):

- `src/app/(redesign)/app/cleaner-dashboard/earnings/page.tsx` — replace the stub body with `return <CleanerEarnings />`. Stays a 1-line server wrapper, no logic.
- `src/components/redesign/cleaner/earnings/CleanerEarnings.tsx` — **Container** (`"use client"`). Fetches via `useStripeConnect` (status + Open-Stripe), `useCleanerAwaitingPayments`, `useCleanerStats`, and computes `deriveEarnings()`. **Does NOT call `useCleanerConnect`** (the embedded `CleanerStripeConnect` owns that hook internally; a second call would spin up a second Account Session). Renders the `CleanerStripeConnect` embed slot **itself, in one fixed JSX position** (the way Slice 3's `CleanerActiveJob` Container owns the stateful `CleanerPhotoCapture` as a sibling), passing `appearance={getRedesignConnectAppearance(resolvedTheme === 'dark')}` behind a `mounted` gate (mirror `PaymentsYourMoney`). Owns the latched `revealed` flag and the Open-Stripe callback plus its `connectError`/`dashboardLoading`.
- `src/components/redesign/cleaner/earnings/CleanerEarningsView.tsx` — **pure presentational**. Renders the framing/copy for each state from `ui/*` primitives **around a single fixed embed slot passed in from the Container** (as a prop / `children`), so the embed node never changes parent across state transitions. The per-state switch may swap the framing card vs the embed's visibility, but must **never wrap or re-parent the embed** (do not put the embed inside a per-state early-return branch). Loading / stripe-disabled / employee / not-set-up / pending / active are framing variations over that one stable slot.
- `src/components/redesign/cleaner/earnings/deriveEarnings.ts` — **pure, React-free**: raw inputs (connect status, awaiting rows, stats, flags) -> typed `EarningsData` (named state enum + clearing rows view-model + activity counts + `isEmpty`). All branching logic lives here so it is unit-testable without rendering Stripe.
- `src/components/redesign/cleaner/earnings/deriveEarnings.test.ts` — Vitest, table-driven, with small `appt()`/`payment()`/`status()` factories (per the `create-tests` skill).
- `src/components/redesign/cleaner/earnings/earnings-types.ts` — `EarningsData` + the state enum. Import `CleanerStats` / `AwaitingPaymentRow` from `@/hooks/useCleanerData`; do not redefine.

## 8. Critical implementation invariants

- **Never unmount the Stripe embed once painted.** The `ConnectComponentsProvider` (inside `CleanerStripeConnect`) must not unmount after first render, or the bank-link popup loses `window.opener` and loops on "Select an account for payouts" (a real prod incident). `shouldShowCleanerConnectSkeleton` + `statusInitializedRef` already keep `statusLoading` sticky-false, and `initedForRef` keeps the instance stable; reuse them and never toggle the skeleton after first load.
- **One fixed embed slot; the reveal flag LATCHES (the blocker fix).** The Container renders `<CleanerStripeConnect appearance={...} />` in one fixed JSX position. A local `revealed` flag controls card-vs-embed in that slot. `revealed` must **latch true and never return to false**: it becomes true on the Set-up button click, OR once `cleanerStatusKind` has **ever** been `'active'`, OR once the embed has mounted. Do **NOT** compute it as `revealedByClick || kind === 'active'`, because Stripe can later flip `onboarding_complete` back to false (a post-activation restriction; the account-status route recomputes it every fetch) and that would unmount a live embed mid-flow. The reveal/skeleton decision keys off the **latched flag + presence of a `connectStatus` snapshot**, never a live loading flag that can re-toggle. The only transition is card -> embed (mount), never embed -> card. `CleanerStripeConnect` then swaps `ConnectAccountOnboarding -> ConnectPayouts` inside the one persistent provider when onboarding completes. Do NOT render the embed under different parent nodes per state.
- **Open-Stripe errors surface at the button.** `handleOpenStripeDashboard`'s `connectError` + `dashboardLoading` belong to the Container's `useStripeConnect` instance, so render them **at the Open-Stripe button** (pop-up-blocked message + spinner), distinct from the embed-internal `connectError` that `CleanerStripeConnect` shows above the iframe. (Legacy `cleaner-dashboard/page.tsx` keeps a page-level `useStripeConnect` for exactly this.)
- **Exactly one `payouts:cleaner:{userId}` realtime sub** exists, inside `useCleanerAwaitingPayments`. Safety comes from the realtime helper's `useId()` topic-uniqueness (no binding-mismatch crash) + exactly one component owning the sub (no duplicate work) + route exclusivity (redesign and legacy never mount together), **not** channel-name dedup. Do not add a second payouts subscription. Activity-count tiles (`useCleanerStats`) are only invalidated by payout events, so they refresh on `staleTime`/focus when a job completes elsewhere; acceptable (optionally add a deduped `appointments:cleaner:{userId}` sub for live counts).
- **Reduced motion:** `AnimatedNumber`/`NumberFlow` and the `.redesign` reduced-motion CSS neutralize automatically; nothing extra required.

## 9. UI implementation and styling source (contract)

The browser-companion mockups produced during this brainstorm are **UX/structure reference ONLY.** Every screen is implemented from our design system: the primitives in `src/components/ui/*` and the tokens in `tailwind.config.js` + `src/app/globals.css` (brand `#0150FC`, Plus Jakarta Sans, warm canvas, soft "pillowy" shadows, the rounded scale). Do **not** copy ad-hoc colors, raw hex, or bespoke classes from a mockup (the amber "Clearing" tone and the dashed embed box in the sketches are placeholders, not design decisions). Status/urgency is signaled with the **Badge/StatusPill vocabulary**, never decorative stripes. If a needed pattern has no primitive yet, build it as a reusable primitive that matches the system. Run `ui-feature-workflow` + `ui-ux-pro-max` at BOTH design and implementation per CLAUDE.md.

Copy rules: cleaner-facing copy says **"office," never "operator"**; **no em dashes** anywhere in UI copy (use a period, comma, parentheses, or "to"); `bank_paid` reads as "Paid out" (handled inside the embed/existing code).

## 10. Testing

- `deriveEarnings.test.ts` co-located, Vitest, table-driven: cover every state branch (stripe-disabled, employee, inactive/pending/active, clearing present/absent, activity counts). `deriveEarnings` takes **only the four count fields** from stats (destructure `completedThisWeek`/`completedJobs`/`totalJobs`/`upcomingJobs` explicitly, never spread the stats object), takes `default_payout_model` as an arg defaulting to `'percentage_contractor'` (no live source until Slice 6, so the employee branch is unit-tested only), and labels clearing amounts *expected/pending*. **Hard assertions:** no money aggregate (`totalEarnings`/`pendingPayouts`) ever appears in the view-model; and the latched-reveal regression, a second `refetchStatus()` after first load neither flips the view back to loading nor unmounts the embed.
- No new API routes are introduced (all reuse), so **no new `*.integration.test.ts`** unless an existing route is touched (it should not be).
- Visual verification with Playwright MCP against the worktree dev server (logged in as `cleaner@nexxus.com`), plus `ui-ux-pro-max` conformance at implementation. Send Bridger screenshots of the **built** screen (he is usually mobile, though this session is desktop).

## 11. Out of scope / deferred

- Native per-job payout-history list (Stripe embed is the history; avoids the `useCleanerPayouts` privacy footgun).
- Period (this week / this month) earnings **dollars** (the data only gives a count cleanly; Stripe owns money; not wanted).
- Full employee/hourly model Earnings (placeholder only; Slice 6 + its own brainstorm).
- Wiring the real `default_payout_model` into the app (Slice 6).
- DB-layer payments-RLS redaction of `payments.amount` for cleaners (separate, riskier change).
- Server-side computation of `cleanerCut` so the full charge never transits the wire for `payout_only` orgs (same deferred server-redaction item as the RLS gap).
- Cancel-during-ACH-debit: a `processing` revenue row on a cancelled appointment can transiently appear in "Still clearing" (the awaiting query has no `appointment.status` filter); accepted until that known payments gap is closed.
- "Message office" (Slice 5).
